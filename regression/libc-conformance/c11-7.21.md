# C11 7.21 Input/output `<stdio.h>`: the two C libraries

> Status 2026-11-01: the survey as taken.  62 probes (`probes/7.21*.c`).
> **rt** (clang + `runtime/`): **36 PASS, 23 DIFFER, 3 NOBUILD**.
> **sh** (stage08 cc + the selfhost library): **40 PASS, 18 DIFFER, 4 NOBUILD**.
> No TIMEOUT, no ORACLE-SPLIT (one ruling, below).

The two libraries share `runtime/printf_enhanced.c`, `dtoa.c` and
`sscanf.c`, so every formatted-I/O finding below is the same in both; they
part only in the stream layer (`runtime/stdio.c` against
`selfhost/stage08/libc`), where the selfhost library does better.

The strong part: everything floating-point in `printf` (%f %F %e %E %g %G:
rounding, halfway cases going to even, exact digits of `DBL_MAX` and the
smallest denormal at %.330f, the %g style choice and trailing zeros, the #
flag, inf/nan spelling), the integer conversions with every flag, width
and precision (including `*`, negative `*`, precision 0 with value 0),
`snprintf` truncation and return value, the `v*printf` forms, and file
handling (fopen modes, append, update-mode switching, fseek/ftell,
fgetpos/fsetpos, rewind, fread/fwrite, remove/rename/tmpfile, setvbuf,
perror).  The weak part is `sscanf`: a 220-line scanner that implements
`%d %i %u %x %X %o %c %s %f %g %e %n %%` and nothing else.

## Summary of gaps

### Wrong behaviour (DIFFER)

**Formatted input, both libraries (`runtime/sscanf.c`)**

1. **No `%[` scansets at all** (7.21.6.2p12).  `sscanf("abcbaxyz",
   "%[abc]%s", a, b)` should return 2 with `a = "abcba"`; it returns 0 and
   assigns nothing.  Negated sets, a leading `]`, `-` first or last: all
   0 (`sscanf-scanset`, `sscanf-c-noskip`).  `sscanf.c` has no `case '['`.
2. **Never returns EOF** (7.21.6.2p16).  `sscanf("", "%d", &a)` and
   `sscanf("   ", "%d", &a)` must return `EOF`; both return 0.  Same for
   `vsscanf` (`sscanf-return`, `vsscanf`).  A caller looping
   `while (sscanf(...) != EOF)` never stops.
3. **The `hh` and `h` modifiers store a full `int`** (7.21.6.2p11):
   `%hhd` into a `signed char[2]` overwrites the neighbouring byte(s), and
   `%hd` into `short[2]` overwrites `[1]`.  That is memory corruption in a
   conforming program.  `%lln` likewise stores only 32 bits (an `int`):
   with the target initialised to -1 the result read back is
   `-4294967285`, not 11 (`sscanf-length`, `sscanf-n-suppress`).  The
   parser skips `h`/`l` letters but only `ll` changes the store.
4. **`j`, `z`, `t`, `L` are unknown**: `"%jd %zu %td"` stops the scan
   (return 3 of 6 in the probe; the targets are untouched), and `%Lf` into
   a `long double` fails (`sscanf-length`, `sscanf-float`).
5. **Missing conversions `%p`, `%a`, and the upper-case `%E %F %G %X`
   twins of the float conversions** (7.21.6.2p12, p14; `%X` does work).
   `%p` makes the `printf("%p")` → `sscanf("%p")` round trip fail
   (returns 0); `sscanf("0x1.8p1", "%la", &d)` returns 0, wanted 3.0;
   `sscanf("2.5", "%F", &f)` returns 0 (`sscanf-pointer`, `sscanf-float`).
   Hex floats through `%lf` do work (`"-0x10"` gives -16).
6. **A field width is ignored for floating conversions** (7.21.6.2p9):
   `sscanf("3.14159", "%4lf%d", &f, &a)` should give 3.14 and 159 (return
   2); it gives 3.14159 and return 1 (`sscanf-width`).
7. **A prefix of a number followed by a non-matching character is
   converted** (7.21.6.2p9-10, footnote 285; see the ruling below).
   `sscanf("25exp", "%lf%7s", &d, rest)` must be a matching failure
   (return 0, `d` unchanged); it returns 2 with `d = 25`, `rest = "exp"`.
   The integer case (`"0xg"` with `%x`) is right.

**Formatted output, both libraries (`runtime/printf_enhanced.c`)**

8. **`hh` and `h` are parsed and then ignored** (7.21.6.1p7).
   `printf("%hhd %hd", 300, 70000)` should print `44 4464`; it prints
   `300 70000`.  `%hhu` of -1 prints 4294967295, not 255
   (`printf-length-convert`).  The `'h'` branch of the length parser only
   advances `fmt`.
9. **No `%n`** (7.21.6.1p8): `printf("ab%ncde", &n)` prints `ab%ncde` and
   leaves `n` alone, for every length modifier (`printf-n`).  There is no
   `case 'n'`.
10. **No `%a` / `%A`** (7.21.6.1p8): printed literally as `%a`
    (`printf-a`; the expected text is the hosts' `0x1p+0`, `0x1.8p+0`,
    `0x0p+0`, `0x1.999999999999ap-4` ...).  It also consumes no argument,
    so every later conversion in the same call reads the wrong one.
11. **`#` with `x`/`X` decides on the first character after precision
    padding** (7.21.6.1p6).  `%#.0x` of 0 prints `0x` (should be empty:
    the prefix is only for nonzero values), and `%#8.4x` of 255 prints
    `    00ff` instead of `  0x00ff` (a nonzero value lost its prefix
    because the precision zeros start with `0`).  The test is
    `conv_str[0] != '0'` after the precision has been applied
    (`printf-oux-alt`).
12. **`%p` ignores the rules for field width** (7.21.6.1p4).  `%20p` gives
    `0x00000000000fffffbc` (zero-filled to the width, the default 10-char
    form `0x0fffffbc` lengthened) and `%-20p` gives `0xfffffbc` padded
    right (a different, unpadded form).  The text of `%p` is
    implementation-defined, but a width must pad it with spaces; the
    probe checks only that (`printf-p`).  The `'p'` case sets
    `zero_pad = true`.
13. **`%ls` prints only the first character** (7.21.6.1p7, `l` with `s`):
    `printf("%ls", L"wide")` gives `w` (`printf-wide`).  The `s` case reads
    a `char *` whatever the modifier; on a little-endian `wchar_t` the
    first character's high bytes are the NUL.

**Streams, rt only (`runtime/stdio.c`)**

14. **`fputc`/`putc`/`putchar` return `c`, not the character written**
    (7.21.7.3p3).  `fputc(0x142, f)` writes `B` and must return 66; rt
    returns 322 (`fgetc-unsigned`, `fputs-puts-putc`).  Both the fast path
    and `fputc_general` `return c`.  sh is right.
15. **A second `ungetc` reports success but replaces the first**
    (7.21.7.10p3, p6).  Only one pushback is guaranteed, so failing the
    second would be fine; succeeding while dropping the first is not.
    After reading `hel` from `hello`, `ungetc('l')` then `ungetc('X')`
    both succeed, `ftell` stays 2 instead of 1, and the stream yields
    `X l o` rather than `X l l o` (`ungetc-eof-position`).  The stream has
    a single `ungetc_char` slot.  sh is right.
16. **`freopen(name, mode, stdin)` succeeds but reading still comes from
    the original standard input** (7.21.5.4p2).  After `freopen("fa.txt",
    "r", stdin)`, `fgetc(stdin)` returns the host's stdin bytes (EOF under
    the harness).  `fread_general` sends `stream == stdin` to `getchar()`,
    which reads the console channel, not `stdin->fd` (`freopen`).  sh is
    right.
17. **`getchar()` returning EOF does not set `feof(stdin)`** (7.21.7.1p3,
    7.21.7.6p3): at the end of `.in`, `getchar() == EOF` but
    `feof(stdin) == 0` (`getchar-stdin`).  Same path as 16.  sh is right.

**Streams, both libraries**

18. **The end-of-file indicator is not sticky** (7.21.7.1p3).  Once
    `feof(f)` is set, `fgetc` must return EOF until `clearerr`, `rewind`,
    a seek or `ungetc`.  After hitting the end and then appending `b`
    through a second stream, both libraries' `fgetc` returns `b` (with
    `feof` still set); after `clearerr` the next `fgetc` returns EOF
    (`feof-ferror-clearerr`).  rt's `fgetc_slow` does not look at
    `stream->eof`.
19. **The C11 exclusive mode `x` is ignored** (7.21.5.3p3, p5).
    `fopen("ex.txt", "wx")` on an existing file must fail; both libraries
    open it, **truncating the file** the program meant to protect
    (`fopen-exclusive`).

### Missing pieces (NOBUILD)

- **`fscanf`, `scanf`, `vscanf`, `vfscanf`** (7.21.6.2, .4, .9, .11): rt
  declares `fscanf`/`scanf` but defines neither; sh has none of the four
  (`fscanf-file`, `scanf-stdin`).  Only string scanning exists.
- **`FOPEN_MAX`** (7.21.1p3), both (`fopen-max`).
- **`tmpnam`, `TMP_MAX`, `L_tmpnam`** (7.21.4.4), sh only (`tmpnam`; rt
  passes).
- `gets` is not in C11 (it was removed), and nothing requires a library
  to lack it, so it is not probed.

### Ruling on the oracle

- **`sscanf-prefix-not-match`** (`.expect` written).  Input `"0xg"` with
  `%x`, `"25exp"` and `"1.5e+z"` with `%lf`.  The input item is the
  longest sequence that is a matching sequence or a prefix of one
  (7.21.6.2p9): `0x`, `25e`, `1.5e+`.  None is a matching sequence, so the
  directive is a matching failure (p10), nothing is assigned, and the
  return is 0; footnote 285 says the function pushes back at most one
  character, so it cannot retreat to `25` and leave `exp`.  glibc assigns
  0, 25 and 1.5 (and has consumed the prefix: rest `g`, `xp`, `z`); macOS
  assigns the same values but pushes the prefix's tail back (rest `xg`,
  `exp`, `e+z`).  Both are wrong by the text, which also works an example
  of the same shape in 7.21.6.2p19-20.  Expected output: `0 7 []` three
  times.  Both SLOW-32 libraries get the `%x` line right and the two
  `%lf` lines wrong, the macOS way.
- Left out rather than ruled: `%5c` against input `"pq"` (input ends
  before the width).  Both hosts return 1 having stored `pq`; SLOW-32
  returns 0.  By p9-10 the item `pq` is not a matching sequence for a
  five-character `%c`, which favours SLOW-32, but whether end of input
  makes it an input failure (and so EOF) is less clear; not probed.

### Seen in passing, outside 7.21

- stage08 cc converts the literal `1e23` to 100000000000000008388608
  (the double above), where `strtod("1e23")` in the same program and
  clang both give 99999999999999991611392: a compiler constant-conversion
  defect (6.4.4.2).  The `printf-f-magnitude` probe spells the exact value
  instead.
- rt's `<stddef.h>` declares `wchar_t` as `int`, but clang's slow32
  target makes `L"..."` an array of `unsigned int`, so
  `wchar_t ws[] = L"wide";` does not compile with clang (7.19p2, 6.4.5p6).
  `printf-wide` uses a pointer instead.
- sh has no `<float.h>` and no `<wchar.h>`; its `<math.h>` has no
  `INFINITY`/`NAN`.  The probes here avoid them.
